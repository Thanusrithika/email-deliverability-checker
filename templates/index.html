How Email Verification Works

1. Syntax & RFC 5322

Checks string structure, consecutive dots, length constraints (RFC 5321: ≤ 254 chars total, ≤ 64 chars local part), and valid top-level domain.

2. DNS MX & Fallback

Queries DNS for Mail Exchanger (MX) records, detects RFC 7505 Null MX records (explicit email rejection), and validates domain resolution via A-record fallback.

3. SMTP Mailbox Handshake

Performs an RFC-compliant SMTP handshake (EHLO, MAIL FROM, RCPT TO). Never transmits email body or DATA.

Why is "Unknown" a Valid and Frequent Result?

1. Catch-All Mail Servers: Many corporate and enterprise mail servers (e.g. Outlook 365, Google Workspace, custom domains) are configured to return 250 OK for all recipient addresses to prevent username harvesting. Because any arbitrary address returns OK, mailbox existence cannot be confirmed, resulting in an accurate Unknown classification.

2. Cloud Hosting Provider Restrictions (Port 25): Cloud hosts (Render, Railway, PythonAnywhere, AWS, DigitalOcean) intentionally block outbound TCP port 25 to prevent spam bots. When deployed in such an environment, the application validates syntax, domain existence, and MX records, but safely falls back to reporting unverified mailboxes as Unknown with detailed explanations.

3. Greylisting & Anti-Spam: Many destination servers intentionally reply with temporary 4xx codes (450 / 451 / 421) to unknown senders to verify retry behavior.
